# 試験の作成方針

`tests/`以下の試験を書く・直す・レビューするときに守ること。CIで「たまに落ちる」試験を何度も直してきた。その原因と決まりをここにまとめる。

## 1. 大原則

- **試験は100%成功しなければならない。** 再実行で通る試験は不合格として扱う。落ちたら、偶然と片付けずに原因を特定して直す。
- **試験の結果を、実時間・実行速度・OSのスケジューリングに左右させない。** 開発機で通るかどうかは根拠にならない。CIのWindows(windows-latest)は、遅さのばらつきが大きい。
- **確かめるのは、終わったときの状態。** 戻り値、終了コード、応答、EOF、記録された内容で判定する。「ある時間内に起きた/起きなかった」では判定しない。

## 2. 絶対時間で待たない

終わるはずの処理は、上限を付けずにそのまま`await`する。上限を付ける理由はない。終わらないならそれが不具合で、検出は試験の外の仕組みがする。

- 止まった試験の検出は、`dotnet test --blame-hang-timeout`だけが担当する(CIでは5分)。止まった試験の名前とダンプは、そこから取る。
- 試験の中では次のものを使わない。
  - 実時間の期限が付いた待ち: `WaitAsync(TimeSpan)`、`CancellationTokenSource(TimeSpan)`、`CancelAfter`、`WaitWithDiagnosticsAsync`、`TestTimeouts.Hang`
  - 時間で待つもの: `Task.Delay`、`Thread.Sleep`、`SpinWait`、時間付きの`WaitOne`
  - ポーリング: 条件が成り立つまで繰り返し確かめる処理(`WaitUntilAsync`、ファイルの出現待ちなど)
- 「一定時間、何も起きないこと」を確かめる試験は書かない。起きないことを確かめたいなら、起こり得た時点より後にある、決まった出来事(次の応答、終了、EOF)まで進めてから、記録に現れていないことを確かめる。
- `TimeSpan`の値を書いてよいのは、偽の時計(`FakeTimeProvider`)に渡す値と、時刻やフレーム間隔のような「データとしての時間」だけ。

## 3. 製品の期限を試験の結果に関わらせない

製品には実時間の期限がある。`ServerBackend`の`readyTimeout`、`probeTimeout`、`cancelTimeout`、`stopTimeout`(quitの待ちはその半分)、`ProcessSupport.ReapBoundedAsync`、入力検査、help取得などだ。既定は数秒で、期限が切れると強制終了やエラーになる。

- **期限を試験しないとき**(本物のプロセスを使う試験の大半): 期限なし(`Timeout.InfiniteTimeSpan`)で作る。試験用の作成補助を経由させ、既定値のまま作らない。
- **期限そのものを試験するとき**: 偽の時計と、偽の相手(プロセスを起動しないもの)で、決まった順に起こす。偽の時計と本物のプロセスを同じ試験で混ぜない(lintで検出する)。
- 例: 2026-11-20、`StreamingBackendTests.ServerDisposeReapsInheritedPipeAfterChildIsReleased`。既定の`stopTimeout`(5秒)のうち、quitの待ちは2.5秒。CIのWindowsでは、孫の起動がそれより遅れた。そのため、プロセスツリーごと強制終了され、試験が孫を探したときには消えていた。

## 4. 本物のプロセスは必要なときだけ使う

- 本物のプロセス(偽エンコーダ、CLI、`cmd.exe`)を使うのは、プロセスでしか確かめられない性質の試験に限る。パイプの継承、EOF、終了コード、プロセスツリーの回収などだ。
- 画面の動作や、移動・先読み・比較などの判断を確かめるなら、プロセスを起動しない偽物で、応答の順番を試験側から決める。偽エンコーダを「便利な相手」として使わない。
- 本物のプロセスを使うときは、次を守る。
  - 進行の合図は、試験側が作った名前付きパイプで受け取る。ファイルでの合図や、ファイルの監視は使わない。
  - **相手が書くものは、相手の終了やほかの出来事を待つ前に読む。** Windowsの名前付きパイプは、バッファを指定しない(0)と、書き込みが相手が読むまで終わらないことがある。読む前に相手の終了を待つと、互いを待って止まる(2026-11-20の`FakeProcessControlTests.InheritedPipesStayOpenUntilOwnedChildIsReleased`)。
  - 相手に`release`などを送る前に、相手の`ready`やPIDを読み終えておく。
  - 偽エンコーダの子に、実時間の期限を持たせない。子が終わる条件は「指示を受け取る」か「制御パイプのEOF」だけにする。試験が失敗しても、パイプを閉じれば子は必ず終わる。
  - `GetProcessById`で取ったプロセスなど、試験が起動していないプロセスの終了を、完了条件にしない。応答とEOFで表す。
  - 後片付けは`finally`で行う。順番は、パイプを閉じる → 起動したプロセスの終了を待つ、とする。失敗したときに最初の例外を消さない。

## 5. テキストの文字コードを明示する

- 出力をリダイレクトしてテキストとして読むときは、`StandardOutputEncoding`と`StandardErrorEncoding`を必ず指定する。偽エンコーダとCLIはUTF-8で書く。`cmd.exe`の内部コマンドは`/u`を付けてUTF-16LEで読む。
- 指定しないとOSの既定のコードページで読まれる。日本語のWindows(CP932)と英語のCI(cp1252)では結果が変わる。
- CIのPythonのように、ツールが標準出力に日本語を書く場合は、`PYTHONIOENCODING: utf-8`などで文字コードを固定する。

## 6. 反射とファイルの合図を使わない

- 非公開のメンバーを反射で読み書きしない(`BindingFlags.NonPublic`、`GetField`など)。状態は、公開されている経路か、試験用に用意した観測点から読む。
- ファイルを進行の合図に使わない(`FAKE_ENCODER_READY_FILE`などの古い方式)。`FAKE_ENCODER_COMMAND_LOG_FILE`や`FAKE_ENCODER_PID_FILE`は、相手の終了後に読む記録としてだけ使う。

## 7. 検査と確認

- `scripts/lint-test-synchronization.py`が、上の禁止事項のうち機械的に見つけられるものを検出する(CIの「試験同期の検査」)。新しい種類の誤りを見つけたら、まずlintに検査を足し、`--self-test`の例も足す。
- 試験を足したり直したりしたら、LinuxとWindowsの両方で全件試験を回す(`dotnet test HWEncVppPreview.sln -c Debug`)。
- 本物のプロセスや同期に関わる試験を変えたら、pushの前に、Windowsでその試験を繰り返し回す。CPUに負荷をかけた状態でも回す。回数と失敗の件数を記録する。1回でも落ちたら原因を直す。
- 落ちた試験を直すときは、その1件だけで終わらせない。同じ形の箇所をほかの試験からも探し、まとめて直すか、lintで検出できるようにする。

## 8. 現状

2026-11-20の時点では、既存の試験にこの方針に反する箇所が多く残っている。試験側の実時間の待ちが約1100か所、既定の期限のまま作る`ServerBackend`/`OneShotBackend`が57か所ある。段階的に直している。新しく書く試験と、手を入れる試験は、この方針に従う。
